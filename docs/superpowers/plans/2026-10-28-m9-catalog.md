# M9 Catalog & Downloads Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Admins publish rights-cleared games (files, art, a verified license) in the console.
Subscribers browse the items their plan allows, install them into a launcher-managed folder with
resumable, checksum-verified downloads, and uninstall them. Installed copies follow each item's
lapse rule. A first-run wizard sets up a new install, and someone who skips everything lands on
the catalog's Starter set. The console gets a dashboard. The launcher becomes **portable**: it
writes nothing outside its own folder.

**Architecture:**
- `apps/api`: a new `storage/` module (`FileStore` interface, `LocalDiskStore`, signed tokens) and
  `catalog/` (items, files, media, licenses, publish gate, license expiry, entitlement filter,
  download issue, install status), `stats/` (dashboard). Admin routes under
  `/v1/admin/catalog/*`, subscriber routes under `/v1/catalog/*`, and `GET /v1/files/:token`
  (Range).
- `apps/launcher`: a portable data root (M9a). Then `main/catalog/`: `CatalogClient` (API calls
  through `AuthService.accessCall`), `DownloadService` (queue, Range resume, SHA-256), `Installer`
  (managed folder, library rows, art), `CatalogSync` (lapse rule). Renderer: a Catalog app
  (Browse · Installed · Downloads), a downloads tray indicator, and the first-run wizard in boot
  routing.
- `apps/admin`: Catalog list + item editor (Metadata · Files · Art · License · Publish), and a
  Dashboard as the landing page.
- **Eight PRs**, same loop as M8 (inline TDD with the ledger
  `.superpowers/sdd/2026-10-28-m9-catalog/progress.md` → lint, typecheck, test, test:e2e → fresh
  Opus reviewer per branch → re-grade by effect, fix Critical/Important failing-first → PR →
  `gh pr checks <n>` → owner OK → squash-merge → main push run):
  **M9-0** M8 deferred minors + this plan (Tasks 0–3, `fix/m8-minors`);
  **M9a** portable data folder (Tasks 4–5, `feat/m9a-portable`);
  **M9b** API catalog admin: storage, items, uploads, license, publish (Tasks 6–8, `feat/m9b-catalog-admin-api`);
  **M9c** API subscriber catalog, downloads, install status (Tasks 9–11, `feat/m9c-catalog-api`);
  **M9d** console Catalog + Dashboard (Tasks 12–13, `feat/m9d-admin-catalog`);
  **M9e** launcher downloads, install, uninstall, sync (Tasks 14–16, `feat/m9e-launcher-downloads`);
  **M9f** launcher Catalog app (Tasks 17–18, `feat/m9f-catalog-app`);
  **M9g** first-run wizard, Starter set, docs, v0.9.0 (Tasks 19–21, `feat/m9g-first-run`).

**Tech Stack:** no new runtime dependencies. Uploads and downloads use Node streams,
`node:crypto` (SHA-256, HMAC) and `fetch`. Charts are hand-drawn SVG in the console (load the
`dataviz` skill before Task 13's chart).

## Owner decisions

Asked in one batch on 2026-10-28; all answered "recommended", plus D50 (portability) added by the
owner, which changes D45's default folder.

- **D40 File storage:** `LocalDiskStore` only in M9 (the API runs locally, D29), behind a
  `FileStore` interface. The R2 `S3Store` comes with production deployment in M10.
- **D41 Uploads:** the console uploads through the API, which computes size and SHA-256. Limit
  4 GiB per file. A file is replaced, never edited. Replacing (or adding/removing) a file on a
  published item bumps the item's `version`.
- **D42 Updates:** the launcher shows **Update available**; the player clicks **Update**. No
  automatic updates.
- **D43 Lapse (FR-CAT-7):** the launcher syncs at boot and hourly. An installed item that was
  unpublished, whose license expired, or that left the player's scopes follows its `on_lapse`:
  `keep` stays playable, marked "No longer in the catalog"; `remove` deletes its files and library
  entry automatically and shows a notice listing them. The admin must pick `on_lapse` (no default;
  publish refuses without it). A lapsed subscription locks the launcher (M8) and removes nothing.
- **D44 License gate (C10):** a license can be marked verified only once its evidence file is
  uploaded (who/when recorded). Publish needs a verified, unexpired license + `on_lapse` + at least
  one `rom` or `disc` file. An expired license unpublishes its item automatically.
- **D45 Install folder:** Settings → Storage gets a **Catalog games folder**: a storage location
  with `managed: true`, last in priority, default `<NextLevel folder>\Catalog` (D50, not
  Documents). Games go to `<folder>\<system folder>\<item slug>\`. Changing it affects new installs
  only.
- **D46 Starter set:** admins tick **Starter set** on items; the row shows the starter items the
  player's scopes allow and is hidden when empty.
- **D47 Catalog UI:** a desktop Catalog app (Browse · Installed · Downloads), keyboard, mouse and
  gamepad; a downloads indicator in the taskbar tray. No catalog inside front-end themes in M9.
- **D48 First-run wizard:** shows while `general.setupCompletedAt` is null. Existing installs (any
  storage location or game) are marked completed silently. The Emulators step offers
  **Locate executable…** and an **Official site** link (the preset's `homepage`). Settings →
  General gets **Run setup again**. No emulator auto-install.
- **D49 Dashboard (FR-ADM-6, D38):** tiles: active subscribers (paying · complimentary), MRR
  (monthly + yearly ÷ 12, per currency), downloads in the last 7 days. Downloads per day (30 days)
  chart, top 10 items (30 days), 10 latest sign-ups, failed payments (past-due). Computed on request.
- **D50 Portable (owner, 2026-10-28):** everything the launcher writes lives inside its own
  folder: settings, library, secrets, logs, caches, Chromium data, temp files, downloads in
  progress and the default Catalog folder. Nothing goes to `%APPDATA%`, `%LOCALAPPDATA%`,
  `%TEMP%`, Documents or other Windows folders. M10's installer and auto-update must keep this
  (recorded in the roadmap's M10 row).

**Calls made in planning (no owner decision; reviewers may challenge):**
- **Portable root.** Packaged: `<folder of NextLevel.exe>\data`. Development:
  `<repo>\.nextlevel-dev\` (gitignored), replacing `%APPDATA%\NextLevel-dev`. `NEXTLEVEL_USER_DATA`
  still overrides in development (e2e). Electron paths `userData`, `sessionData` (`<data>\chromium`),
  `logs`, `crashDumps` (`<data>\crashes`) and `temp` (`<data>\temp`, emptied at boot) are all set
  before `ready`. A folder the launcher can't write (e.g. under Program Files) shows a dialog
  ("NextLevel can't write to its folder — move it somewhere you can write, like C:\NextLevel")
  and quits.
- **Moving old data in.** At the first portable boot, when `<data>\settings.json` doesn't exist
  and the old `%APPDATA%\NextLevel` (packaged) or `%APPDATA%\NextLevel-dev` (development) does,
  the launcher copies it in, checks every file's size, then deletes the old folder. Any failure
  removes the partial copy, keeps the old folder untouched, logs, and shows an error dialog. It
  doesn't quietly start empty.
- **A moved folder.** `general.lastRoot` (internal, no Settings field, like `setupCompletedAt`)
  records the NextLevel folder. When it differs at boot (another drive letter or PC), every
  settings path under the old root is rewritten to the new root (storage locations, assets,
  themes, central media folder, emulator executables), after a settings backup. Paths outside
  the folder are left as they are.
- **Secrets on another PC.** `secrets.bin` is DPAPI-encrypted for the Windows user. On another
  PC or user it can't be decrypted: the launcher treats it as empty (sign in again, re-enter
  ScreenScraper credentials) instead of failing, and logs once.
- **Start with Windows** stays (off by default, user opt-in): it is a Windows Run registry entry,
  not a file, and turning the option off removes it. The Settings field says so.
- Admins see every published item in the launcher (their entitlement has every scope). Drafts are
  console-only. A subscriber asking for an item outside their scopes (by id, download or status)
  gets `NOT_FOUND`, never a hint it exists (C8). Status `none`/`suspended` → `SUBSCRIPTION_REQUIRED`/`SUSPENDED`
  as on other device routes.
- One license per item (`catalog_items.license_id`, not shared). `PUT …/license` replaces it and
  clears verification; a published item whose license is replaced is unpublished in the same
  transaction (audited).
- Download URLs: `<publicUrl>/v1/files/<token>`, token = base64url payload
  `{ k: 'file'|'media', id, u: userId, d: deviceId, exp }` + HMAC-SHA256 with a key derived from
  `JWT_SECRET` (`hkdf`, label `nextlevel-files`). Files 10 minutes; media 1 hour. The files route
  refuses a revoked device or a suspended user. The request log records the route pattern
  (`/v1/files/:token`), never the token.
- `downloads.ip_hash` = HMAC-SHA256 of the IP with a key derived from `JWT_SECRET` (label
  `nextlevel-ip`). Rows older than 12 months are deleted by the hourly maintenance job, which also
  expires licenses. Issuing download URLs is limited to 60 per hour per user (per POST, not per file).
- System actions (license expiry) are audited with a null actor: `audit_log.actor_id` becomes
  nullable; the console shows "System". New audit actions: `item.create`, `item.update`,
  `item.file.add`, `item.file.remove`, `item.media.set`, `item.media.remove`, `item.license`,
  `item.license.verify`, `item.publish`, `item.unpublish` (target type `item`).
- Install status replaces `GET /v1/catalog/changes?since=` with
  `POST /v1/catalog/status { items: [{ id, version }] (≤ 5,000) }` →
  `{ items: [{ id, state: 'current'|'update'|'gone', version, onLapse }] }`. A `since` list can't
  see a scope change for one user; the launcher already knows what it installed. `gone` covers
  unpublished, license expired, outside the user's scopes, or unknown id.
- Launcher downloads run one at a time. A queued download is stored in `library.db`, so the queue
  and partial files (`<data>\downloads\<downloadId>\<fileId>.part`) survive restarts. An expired
  URL (`401`/`403`/`410` from the files route) is re-requested once per file; a second refusal
  fails the download. A disk with less free space than the remaining bytes fails it at once
  (`diskFull`).
- Uninstall deletes only the files the installer recorded (`catalog_installs.files`) inside the
  managed location, then the item folder if empty, then the game row (cascade). A game row with
  `source = 'local'` is never touched. A game that is a favorite or in a collection needs
  `confirm: true` (US-E3); the renderer asks.
- A scan that finds an installed catalog file keeps the row's `source = 'catalog'` and
  `catalog_item_id` (the upsert never downgrades it).
- Popular systems pre-checked in the wizard: `POPULAR_SYSTEM_IDS` in `packages/system-catalog`
  (NES, SNES, N64, Game Boy, GBC, GBA, Genesis/Mega Drive, Master System, PlayStation, PS2, Arcade
  (MAME); ids checked against `systems.json` in Task 19).

## Global Constraints

- Everything from the M7/M8 plans still holds: Node 24 erasable TS in `apps/api`, every route
  declares `config.role`, error envelope via `apiError(code)`, response schemas without
  transforms, request log = method + route pattern, migrations generated then Prettier'd,
  `audited()` for every admin mutation (change + audit in one transaction).
- Contracts first: every new HTTP body, IPC channel and event gets a Zod schema in
  `packages/shared` (`src/api/catalog.ts`, `src/api/stats.ts`, `src/ipc/catalogContract.ts`)
  before its code.
- No commercial ROMs, BIOS or links to them anywhere. Fixtures are deterministic dummy bytes
  (`fixtures/catalog/`, 5 items, test-strategy §2) with homebrew-style made-up titles.
- No secrets in logs: no tokens, no download URLs, no IPs (only `ip_hash`), no evidence contents.
- Files ≤ 400 lines; split before crossing. All user-visible strings through i18n (en + pt-BR).
- Launcher writes only inside the portable root (D50) or inside folders the user picked.
  `os.tmpdir()`, `app.getPath('temp'|'documents'|'appData')` are not used anywhere after M9a
  (a lint `no-restricted-properties`/grep test enforces it, Task 4).
- Atomic writes for launcher files; transactions for multi-row changes (install, uninstall,
  publish).
- Limits: upload 4 GiB/file (`4 * 1024 ** 3`); file URLs 10 min, media URLs 1 h; download issue
  60/hour/user; status body ≤ 5,000 items; catalog page `limit` 1–100 (default 50); `q` ≤ 100
  chars; slug `^[a-z0-9]+(-[a-z0-9]+)*$` ≤ 60; filename = a single path segment, 1–200 chars, no
  `\ / : * ? " < > |`, no control characters, not `.`/`..`, no trailing dot or space, not a
  Windows reserved name (`CON`, `NUL`, `COM1`…), extension in the system's extensions for
  `rom`/`disc` files.

## Review Focus

1. **A download token in the wrong place.** Tokens and URLs must not appear in API or launcher
   logs, and a token for one user/device must fail for another device, a revoked device or a
   suspended user. Tests: Task 10 "the request log never contains the token", "a revoked device's
   token is refused"; Task 14 "download URLs are never logged".
2. **A filename or slug from the API escaping the managed folder.** The launcher re-validates every
   filename and slug from the API with the shared `safeFilename`/slug rules before joining paths
   and refuses `..\`, absolute or reserved names, even if the API were compromised. Tests: Task 6
   `safeFilename` cases; Task 15 "an item whose filename escapes the item folder is refused and
   nothing is written".
3. **Quitting or losing the network mid-download.** The partial file resumes from its size after a
   restart, an expired URL is re-requested, and a partial file never reaches the library. Tests:
   Task 14 "resumes from the .part size after a restart", "an expired URL is re-requested once",
   "a cut connection pauses with network, not failed".
4. **A scan or uninstall touching the wrong rows.** A scan keeps catalog rows catalog; uninstall
   never deletes a local ROM, even one at the same relative path in another location. Tests: Task
   15 "a rescan keeps source catalog", "uninstall leaves a local game with the same rel path".
5. **The portable folder moved, copied or read-only.** Another drive letter rewrites paths under
   the old root; another PC boots with empty secrets and asks to sign in; a read-only folder shows
   the dialog instead of crashing. Tests: Task 5 `relocatePaths` cases, "undecryptable secrets
   read as empty"; Task 4 `checkWritable` refusal.
